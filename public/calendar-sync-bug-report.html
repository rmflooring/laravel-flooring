Bug Root Cause

The sync method syncNow() uses a 4-column lookup to find an existing link, but a 2-column key to upsert it. These two queries are logically inconsistent — the lookup almost always misses, causing an unconditional new CalendarEvent insert on every sync run for every user.

app/Http/Controllers/MicrosoftCalendarConnectController.php — lines 401–456

The lookup (lines 401–405) — user-scoped, 4 conditions

$link = ExternalEventLink::where('provider', 'microsoft')
    ->where('microsoft_account_id', $account->id)   // ← scoped to THIS user
    ->where('external_calendar_id', $cal->calendar_id)
    ->where('external_event_id', $externalEventId)
    ->first();

The upsert (lines 445–448) — global, only 2 conditions

ExternalEventLink::updateOrCreate(
    [
        'provider'           => 'microsoft',
        'external_event_id'  => $externalEventId,  // ← no user scope!
    ],
    [
        'microsoft_account_id' => $account->id,      // ← overwrites previous user's ID
        'calendar_event_id'    => $calendarEvent->id,
        ...
    ]
);

The DB unique constraint matches the upsert keys, not the lookup keys

database/migrations/2026_01_13_010253_create_external_event_links_table.php
// Only 2 columns — one link globally per Graph event ID, across ALL users
$table->unique(['provider', 'external_event_id']);

There is no unique constraint on calendar_events and no graph_event_id column — nothing at the DB level prevents the same MS Graph event being inserted millions of times.

Flow What Happens Each Sync Cycle

For any calendar event shared between multiple users (e.g. a team meeting):

User A syncs (10:00)

Lookup with microsoft_account_id = A → no row found → new CalendarEvent() + save() creates row #1 → updateOrCreate creates an ExternalEventLink pointing to #1, owned by A.

User B syncs (10:02)

Lookup with microsoft_account_id = B → finds nothing (the link has A's account_id) → creates row #2 → updateOrCreate updates the existing link: now owned by B, pointing to #2. Row #1 is now orphaned.

User A syncs again (10:10)

Lookup finds nothing again → creates row #3 → link updates back to A. Row #2 orphaned.

Repeats every 10 minutes, forever

With 5 connected users and hundreds of shared events, ~43 orphaned CalendarEvent rows are created per timestamp. The ExternalEventLink table just bounces between users, always pointing to the most recently created row. Every previous row is abandoned.

Fix Proposed Solutions

A Per-user links — Recommended

Matches the existing code intent: owner_user_id is set on each CalendarEvent, so each user is meant to have their own row per event. Requires one migration and a one-line controller fix.

Migration

Schema::table('external_event_links', function (Blueprint $table) {
    $table->dropUnique(['provider', 'external_event_id']);
    $table->unique(['provider', 'microsoft_account_id', 'external_event_id']);
});

Controller fix — syncNow() lines 445–448

ExternalEventLink::updateOrCreate(
    [
        'provider'             => 'microsoft',
        'microsoft_account_id' => $account->id,   // ← ADD THIS LINE
        'external_event_id'    => $externalEventId,
    ],
    [
        'external_calendar_id' => $cal->calendar_id,
        'calendar_event_id'    => $calendarEvent->id,
        'last_synced_at'       => now(),
    ]
);

B Shared event — simpler, no migration

One CalendarEvent per MS Graph event, shared across all users. Fix: change the lookup to drop microsoft_account_id and external_calendar_id from the WHERE clause so it matches the existing DB unique key. No migration needed, but all users see the same event row (may limit per-user customisation).

$link = ExternalEventLink::where('provider', 'microsoft')
    ->where('external_event_id', $externalEventId)   // only 2 conditions
    ->first();

Cleanup Safe Plan for Removing 16.7M Orphaned Rows

Important: Deploy and verify the fix above before running any cleanup. If you clean up first, the table will just refill within minutes.
  1. Verify the orphan count before touching anything 
    SELECT COUNT(*) FROM calendar_events
WHERE id NOT IN (SELECT calendar_event_id FROM external_event_links)
AND related_type IS NULL;

    The related_type IS NULL guard ensures we never touch events that are organically linked to jobs or opportunities, even if they have no external link entry.

  2. Delete in batches of 100,000 (avoids long table locks) 
    -- Run this repeatedly until rows affected = 0
DELETE FROM calendar_events
WHERE id NOT IN (SELECT calendar_event_id FROM external_event_links)
AND related_type IS NULL
ORDER BY id
LIMIT 100000;

    ~167 iterations to clear ~16.7M rows. Run via a loop in tinker or a one-off Artisan command. Each batch should take a few seconds.

  3. Reclaim disk space 
    OPTIMIZE TABLE calendar_events;

    Rewrites the table and returns the ~5.4 GB. This may take a few minutes on a large table — run during off-hours or a low-traffic window.

  4. Confirm the table is clean 
    SELECT COUNT(*) FROM calendar_events;   -- expect a few hundred at most
SELECT COUNT(*) FROM external_event_links; -- should match calendar_events ~1:1
